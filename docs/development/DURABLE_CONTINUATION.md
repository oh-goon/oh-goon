# Durable continuation authority

**Scope.** This recovery graph and archive protocol applies when the task
explicitly continues an archive-managed campaign or requests a portable
checkpoint. Ordinary Git-backed contributions use the selected branch/commit
and reviewed working-tree changes as source, with normal Git commits and
authorized synchronization for preservation. A GitHub clone does not require
historical checkpoints, a `RECOVERY_STORE`, or archive handoffs. Creating a Git
worktree for an archive-managed task does not replace its verified recovery
chain. Repository ownership, regression, and change-impact rules apply to both.

Archive-managed development, repair, qualification, and dogfood campaigns must survive total loss of conversational state **and** loss of the current execution container/workspace.

The governing invariant is:

> **Changing sessions or losing the current container may lose all conversational and workspace state without losing project authority, completed-phase evidence, or the remaining execution plan.**

Chat history, model memory, an open terminal, `/mnt/data`, and an uncheckpointed working tree are never continuation authority. They are disposable working aids. A fresh session must be able to reconstruct the campaign from persistent project state alone.

## Continuation model

Do not use this model:

```text
previous chat/session/container
  -> remember source and remaining plan
  -> continue
```

Use this model:

```text
persistent RECOVERY_HEAD
  -> digest-bound publication receipt
  -> exact immutable source archive + proof + continuation objects
  -> verify source/archive/continuation identities
  -> read explicit next executable phase
  -> continue in a new disposable workspace
```

A checkpoint is complete only when a worker with zero useful conversation history can answer from durable state:

- What exact source/archive is current authority?
- What digest and canonical source identity prove those bytes?
- Which phases are completed, open, blocked, or incomplete?
- Which proof receipts belong to the current authority?
- What qualification state is actually proven?
- What is the one next executable phase?
- What receipt/HEAD chain proves that this continuation state was committed atomically?

If any answer depends on remembered chat context or vanished container bytes, the campaign is not durably checkpointed.

## Recovery graph is the authority

`RECOVERY_HEAD.json` is the atomic mutable pointer. It binds the committed source identity, publication receipt digest, continuation-state digest, proof level, qualification state, campaign, generation, and exact previous HEAD identity.

The publication receipt binds:

- campaign/generation and parent/result source identities;
- source archive digest, size, and immutable object key;
- exact normalized continuation-input digest;
- exact immutable continuation-state digest and object key;
- structured recovery-proof receipt digest when present;
- proof level and qualification state.

The immutable continuation object is generated by the recovery owner. Callers do **not** author source/archive/generation identities. Recovery derives those facts from the source it actually packages and publishes, then combines them with the supplied phase ledger.

The committed graph is therefore:

```text
RECOVERY_HEAD.json
  -> publication receipt
      -> immutable source archive
      -> optional structured proof receipt
      -> immutable machine-readable continuation state
```

HEAD advancement remains:

```text
BUILD
  -> VERIFY LOCAL
  -> PUBLISH IMMUTABLE ARCHIVE
  -> VERIFY DURABLE ARCHIVE
  -> PUBLISH/VERIFY PROOF + CONTINUATION
  -> PUBLISH RECEIPT
  -> CAS HEAD
  -> COMMITTED
```

A crash before successful HEAD CAS leaves the previous HEAD authoritative. A crash after successful CAS leaves the new generation fully reconstructable. Unreferenced immutable objects from an interrupted attempt are not authority.

This continuation binding is a deliberate recovery-schema boundary (`RECOVERY_HEAD` v3 / publication receipt v2). A legacy recovery HEAD that does not bind continuation state is **not** silently upgraded or treated as sufficient continuation authority. Start the new recovery lineage from the exact verified persisted source authority and an explicit continuation ledger.

## Continuation input versus committed continuation state

A campaign supplies a small authoring input to `recovery-checkpoint`. This input is **intent**, not authority:

```json
{
  "schema": "oh-goon-development-continuation-input-v1",
  "completed_phases": [
    {"id": "phase-a", "state": "NEWLY_CLOSED"}
  ],
  "open_phases": [
    {"id": "phase-b", "state": "OPEN"}
  ],
  "proof_receipts": [
    {"selection": "focused owner regression", "outcome": "PASS"}
  ],
  "qualification_state": "NATIVE-QUALIFICATION-INCOMPLETE",
  "next_executable_phase": "phase-b",
  "durability_invariant": "Changing sessions or losing the current container may lose all conversational and workspace state without losing project authority, completed-phase evidence, or the remaining execution plan."
}
```

The recovery owner validates the ledger, packages the exact source, and emits the authoritative `oh-goon-development-continuation-v1` object. Its `current_authority` is filled from observed facts such as VERSION, campaign/generation, parent/result source identity, archive digest/size/object key, proof-receipt identity, and proof level.

The committed object has this authority shape (values shown here are placeholders; recovery writes the observed values):

```json
{
  "schema": "oh-goon-development-continuation-v1",
  "current_authority": {
    "version": "...",
    "campaign_id": "...",
    "generation": 1,
    "parent_source_identity": "sha256:...",
    "source_identity": "sha256:...",
    "archive_sha256": "...",
    "archive_size": 0,
    "object_key": "objects/sha256/...",
    "recovery_proof_receipt_sha256": null,
    "proof_level": "NONE"
  },
  "completed_phases": [],
  "open_phases": [],
  "proof_receipts": [],
  "qualification_state": "NATIVE-QUALIFICATION-INCOMPLETE",
  "next_executable_phase": null
}
```

`next_executable_phase` must name an entry in `open_phases`. When no open phases remain it must be `null`. `qualification_state` must match the checkpoint qualification state. These checks prevent prose or stale local state from silently selecting work that the committed ledger does not contain.

`next_executable_phase` is exactly **one bounded executable phase**, not a shell recipe or a convenience list of later phases. It must never span a required mutation checkpoint boundary. If a phase changes source, dependency locks, generated authority, recovery state, or another durable authority, persist and independently read back that child generation before another mutation begins. Ordered qualification ladders live in `open_phases`, while `next_executable_phase` names the first currently admissible member. Successful read-only qualification may continue locally through the ordered ladder without a ledger-only generation; after workspace/session loss those proofs are rerun from the latest verified full checkpoint and are never promoted from memory.

See [`RECOVERY_CONTINUATION_INPUT.example.json`](RECOVERY_CONTINUATION_INPUT.example.json) for a copyable authoring shape.

## Persistence cadence: keep the sweep large, keep the loss window small

Persistence is event-driven rather than version-driven. A large cleanup/dogfood campaign may still converge into one DEVELOPMENT candidate, but it must not leave hours of proven work only inside one disposable container.

Persist recovery state at these boundaries:

1. **Before the first source mutation.** Commit the starting source authority plus the planned open-phase ledger. This replaces reliance on a chat/session plan.
2. **After each coherent durable-byte behavior/authority change plus focused proof.** Update completed/open phases and checkpoint before depending on more mutable work.
3. **After every meaningful mutation closure plus its focused proof.** Persist the next recovery generation and independently read it back **before starting the next mutation**. A changed source/lock/generated/recovery closure must not sit only in the disposable working tree while unrelated follow-on mutation begins. Read-only qualification PASS may continue in the same full-checkpoint workspace and is rerun after workspace loss.
4. **Before a risky or long operation** that could reset the execution environment, exhaust a session, or materially enlarge the reconstruction cost.
5. **Before intentionally changing sessions or handing work to another worker.** Verify `recovery-status` from the persistent store first.
6. **Whenever container/session survival is uncertain.** Treat uncertainty itself as a persistence boundary: stop extending the mutable work, checkpoint the coherent proven batch, copy the complete recovery graph to durable storage, and independently read it back before continuing.
7. **At the final candidate boundary.** Persist the exact candidate, proof/qualification state, remaining ledger, and generated human projection, then read it back independently.

A checkpoint is not safely complete merely because `recovery-checkpoint` succeeded in the disposable container. Before depending on that generation, durable storage must contain the exact source archive, `RECOVERY_HEAD.json`, publication receipt, continuation object, and any bound proof object; an independent read-back must verify their expected digests/identities. A partial upload is `PERSISTENCE-INCOMPLETE`, not a durable generation. Do not continue mutable work from a `PERSISTENCE-INCOMPLETE` generation.

Several recovery generations may point at the same VERSION while a large semantic sweep is in progress. Recovery generations are durability boundaries for changed bytes, not release/version churn. Prefer small, independently verified mutation generations over one large unpersisted mutation span; read-only proof runs do not create empty generations.

### Micro-checkpoint rule

Treat each meaningful **mutation closure** as a **micro-checkpoint boundary**. A micro-checkpoint is small by design: one authority decision that changes durable bytes, one coherent repair, or one generated/dependency/recovery authority change plus the focused proof that makes it trustworthy. Do not create empty ledger-only generations for read-only qualification PASS.

Use this cadence:

```text
verified parent authority
  -> one coherent mutation
  -> focused proof
  -> durable micro-checkpoint
  -> independent read-back
  -> read-only qualification ladder and/or next coherent mutation
```

Create a new durable micro-checkpoint whenever any of these becomes true:

- an authority owner or package/module boundary changes;
- a hidden-authority/cucumber family is closed with a regression;
- a generated or dependency authority changes;
- a qualification or repair step rewrites durable source/lock/generated/recovery authority;
- work reaches an external block such as network, package publication, unavailable native materialization, or required human review;
- the next step would make rollback/reconstruction materially harder than replaying the just-closed change.

A micro-checkpoint may share the same target release and DEVELOPMENT version as its siblings. Name the durable recovery generation monotonically (for example `GEN45_M1`, `GEN45_M2`, then the final sealed `GEN45`) so later workers can distinguish incremental durability boundaries from release/version changes. Naming is descriptive only: the committed archive digest, canonical source identity, recovery receipt, continuation object, and independently read-back HEAD remain authority.

**Do not start the next meaningful mutation until the previous mutation checkpoint has been persisted and independently read back.** If persistence/read-back fails, mark the boundary `PERSISTENCE-INCOMPLETE`, stop mutation, and repair durability first. If a session disappears, resume from the newest independently read-back full checkpoint; discard remembered local edits and rerun any read-only qualification that was not captured by a later changed-byte checkpoint.

For broad qualification ladders, keep commands ordered and fail-fast, but distinguish execution failure boundaries from persistence boundaries. Execute the committed first admissible phase; if it changes durable authority, checkpoint/read back before continuing. If it is read-only and passes, the same restored full-checkpoint workspace may continue to the next ordered read-only phase. A later session must rerun those proofs rather than claim remembered PASS.

The final generation seal is not a substitute for mutation checkpoints. Its purpose is to converge already-durable changed-byte closures into the next continuation authority, not to rescue a long unpersisted mutation session.

If the current container disappears after the last independently read-back generation, everything after that generation is `LOST_UNPERSISTED`. Resume from that verified committed HEAD and reapply only the still-open phase. Never promote remembered edits, locally-created-but-unverified recovery objects, or remembered PASS results into authority.

### Qualification and release closure cadence

**Separate mutation durability from release qualification.** Small implementation checkpoints remain mandatory at meaningful changed-byte/semantic-authority boundaries, with focused regression evidence and independent durable read-back. They are **working candidates**, not miniature releases. Do not run or require the full native WSL, browser, catalog, certification, publication or release ladder for each micro-checkpoint, and do not create a new checkpoint merely because a read-only verification command passed.

For a bounded campaign, declare the complete ordered qualification/release gate once and execute it at **one explicit closure boundary** after the last planned implementation slice and adversarial re-attack. Related documentation, QA and non-authority inspection changes may share one small checkpoint when one coherent focused proof covers them; do not combine independently risky admission, execution, security, lock or recovery-authority changes just to reduce checkpoint count. Never defer the focused tests that make an individual mutation safe to persist.

The closure is a **single qualification transaction**, not permission to skip gates: start from the newest independently verified durable source identity; run the full required native/integration/release ladder against that exact candidate, preserve per-gate outcomes and failing evidence, and only seal or publish if every required gate is green. Qualification must not borrow PASS results from older identities or prior sessions. If the environment cannot run a required gate, record `NOT_RUN` or `BLOCKED`, retain an unsealed working candidate, and do not claim release readiness.

A reproduced defect during closure interrupts the transaction: implement a narrow fix with a focused regression, persist/read back a new small changed-byte checkpoint, then restart affected qualification on the **new exact source identity**. Never attach old candidate receipts to changed bytes. A source/lock/generated-authority mutation must not be hidden inside a read-only gate. Read-only gates may execute consecutively without ledger-only checkpoints; after workspace loss rerun any evidence not durably bound to the exact source authority.

### Risk-selected verification before the final release ladder

A campaign is divided into coherent implementation groups with one integration
gate per group and one full release qualification after the final group. A
group is not permission to batch independent authority decisions in a single
source checkpoint; persist and read back each semantic mutation first. Current
execution owners and admission boundaries are described in
[Architecture](../ARCHITECTURE.md#execution-environment-and-admission) and
[current architecture decisions](ARCHITECTURE_DECISIONS.md).

Before touching files, identify which **semantics and effect authorities** change and declare the smallest trustworthy tests: documentation/QA/read-only projections → focused documentation/fixture checks; schema/lock/generated/native authority → focused native contract check; admission/identity/trust → negative/freshness/replay tests; sandbox/credentials/network/teardown/recovery → native isolation, failure-injection and quiescence tests **before activating** the path; journal/evaluator/terminal trust → causal, property and authenticity tests. Do not infer test risk from file count, helper naming, or historical change size.

At each group gate, run the *union of relevant cross-owner tests* once on the group's current exact snapshot; do not blindly call the entire native WSL+browser+certification+release ladder. An expensive test is required when only its native environment can establish the security claim. Record each selected gate, exact command, source/lock/runtime identity, PASS/FAIL/BLOCKED/NOT_RUN, and why an omitted gate is genuinely **NOT_AFFECTED**. An omission is not a PASS.

A focused/group result is reusable for diagnosis only while the source and its asserted dependencies are unchanged. A new candidate does not inherit release PASS from old bytes. The final release transaction always runs the full mandatory matrix on one independently restored candidate. If a critical check is blocked, stop the affected unsafe work rather than change native tool authority or promote a mocked proof. A defect fix changes bytes and requires a focused regression + persisted child before requalification. Do not create a new recovery generation merely for a read-only PASS.

### Micro-checkpoint size is semantic, not temporal

Frequent persistence alone is not sufficient. A checkpoint can be durable and still be too broad if it contains several independent authority decisions that have not each survived their own focused attack.

The two goals are different and both are required:

```text
small checkpoints
    -> no work lost if the agent/session/workspace dies

small semantic slices
    -> failed later testing cannot invalidate three unrelated repairs
```

Define a semantic slice as **one independently testable authority question** with one owner and a focused regression/proof. The slice boundary is where another authority question could be changed, reverted, or attacked independently without changing the already-closed answer.

For example, a larger native-tool repair might expose all of these at once:

```text
canonical executable identity
native runtime selection
native dependency preparation
```

They share one feature area, but they are three semantic slices. Do not implement all three and then rely on one later broad qualification run to discover which assumption was wrong. Close them serially:

```text
verified parent
  -> change authority question A only
  -> focused regression + adversarial attack for A
  -> seal durable child A
  -> independently read back child A

child A
  -> change authority question B only
  -> focused regression + adversarial attack for B
  -> seal durable child B
  -> independently read back child B

child B
  -> change authority question C only
  -> ...
```

The rule is therefore stronger than "checkpoint often":

> **Do not begin the next independent authority mutation merely because the current working tree is still alive. First prove, seal, persist, and independently read back the current semantic slice.**

When a focused test or attack finds a defect inside the current slice, repair that slice and rerun its proof before sealing. Do **not** use the discovery as a reason to pull the next planned authority change into the same mutable batch. Conversely, a read-only broader qualification failure may require reopening the sealed slice only when evidence shows that slice is actually responsible; unrelated sealed siblings remain durable authority and are not reconstructed from scratch.

This controls two different loss radii:

- **workspace-loss radius** — bounded by how frequently changed durable bytes are persisted;
- **semantic-repair radius** — bounded by how many independent authority decisions are allowed into one mutable checkpoint.

The target is one small radius for each. A broad half-proven checkpoint may satisfy the first and still fail the second.

Historical lesson: the GEN45 native-uv repair demonstrated that the durable checkpoint mechanism could preserve completed work across iterations while an overly broad repair batch still required multiple later authority corrections. The correction is not fewer checkpoints or more remembered test results; it is **one semantic authority closure per durable mutation checkpoint**, with the next slice starting only after independent read-back.

### Newest-authority selection at session start

Do not equate "latest checkpoint" with the newest filename, newest full archive, or newest filesystem modification time. Continuation authority is the **highest independently verified parent-linked recovery chain**.

Resolve it in this order:

1. Prefer the committed and verified `RECOVERY_HEAD.json` plus its digest-bound publication receipt, continuation object, source archive, and proof objects.
2. If working from exported/manual micro-checkpoints, identify the newest complete full checkpoint and apply every later verified delta whose parent digest/generation links continue that chain.
3. Verify each delta/archive digest and the reconstructed canonical source identity before treating the result as source authority.
4. Choose the highest proven child in that chain. A verified later delta supersedes its older full parent for continuation even when the older/full artifact has a newer mtime.
5. If a purported newest child is missing, has a broken parent link, or cannot be independently read back, stop with `PERSISTENCE-INCOMPLETE`; do **not** silently resume from an older generation and redo or overwrite already-durable work.

Example:

```text
GEN45_M5 full checkpoint
  -> GEN45_M6 verified delta
  -> GEN45_M7 verified delta
  -> GEN45_M8 verified delta
```

The continuation authority is reconstructed `GEN45_M8`, not `GEN45_M5`. The full checkpoint is the materialization base; it is not the latest semantic authority once verified descendants exist. Monotonic names help humans discover candidates, but only verified parentage/digests and canonical identity make the chain authoritative.

### Portable/exported micro-checkpoint fallback

The repository-owned `RECOVERY_STORE` is preferred because its committed HEAD, receipt, continuation object, proof object, and content-addressed source archive already form one verifiable graph. When the durable medium can store only exported files rather than that live directory, the export is **transport of the same continuation facts**, not a second recovery authority.

Before an exported full checkpoint or delta is allowed to become the parent of more work, durable storage must contain both its payload and a machine-readable sidecar/manifest that binds at least:

- the generation/micro-checkpoint identity and payload SHA-256;
- the parent generation and parent payload/HEAD digest, except for the lineage root;
- for a delta, the base full-checkpoint generation and SHA-256 plus exact changed-file digests;
- the reconstructed canonical source identity and canonical file count;
- the completed/open phase ledger, qualification/proof state, and exactly one `next_executable_phase`;
- evidence that the stored payload and sidecar were independently read back and reproduced the expected identities.

Upload/read-back the payload and its sidecar as one persistence boundary **before** starting the next closure. A filename without a verified sidecar is only a navigation hint. A sidecar without its payload is `PERSISTENCE-INCOMPLETE`. A delta whose parent/base artifact is absent or digest-mismatched is `PERSISTENCE-INCOMPLETE`. A final sealed full checkpoint must bind its last micro-checkpoint parent; once independently verified, that sealed child supersedes the reconstructed intermediate chain as the easiest materialization authority without erasing the chain's evidence.

Never extract an exported delta/archive directly into canonical source. Exported deltas are **transport-only archives**: canonical source bytes live under a top-level `payload/` namespace, while manifests, checksums, and human guidance remain outside `payload/`. A delta ZIP must never expose a runnable checkout root such as `Makefile`, `backend/`, or `frontend/` at archive root. Extract the archive into an external staging directory, verify its payload/sidecar/parent/base digests there, then **apply only the source payload paths declared by the verified manifest** by stripping the verified `payload/` transport prefix. The manifest, sidecar, checksums, handoff text, and other recovery transport stay in staging and must never be copied into the checkout. After applying the declared source payload, recompute the canonical source identity and file count before the reconstructed child becomes authority. A naïve whole-archive extraction into the checkout, or executing commands from an extracted delta directory, is invalid even when the source-file bytes themselves are correct.

## Repository-owned commands

Use a persistent `RECOVERY_STORE` outside the disposable working tree. Recovery transport is not source: keep the continuation input, human handoff projection, restored destination, patches, archives, evidence, and other recovery artifacts outside the checkout they protect.

Create or advance a checkpoint:

```bash
make recovery-checkpoint \
  RECOVERY_STORE=/durable/oh-goon-recovery \
  RECOVERY_CAMPAIGN_ID=<campaign> \
  RECOVERY_EXPECTED_GENERATION=<generation> \
  RECOVERY_EXPECTED_HEAD_SHA256=<exact-head-sha-or-empty-for-generation-0> \
  RECOVERY_CONTINUATION_INPUT=/durable/continuation-input.json
```

The continuation input must remain outside canonical source and is read into the recovery command from that external transport path. The **committed generated continuation object in `RECOVERY_STORE`** is authority after CAS. Do not copy the authoring input into the checkout and do not treat it as a second source of truth.

Verify current recovery authority and print machine-readable state:

```bash
make recovery-status RECOVERY_STORE=/durable/oh-goon-recovery
```

Generate a human-readable handoff directly from verified committed state:

```bash
make recovery-status \
  RECOVERY_STORE=/durable/oh-goon-recovery \
  RECOVERY_FORMAT=markdown > /durable/oh-goon-recovery-handoff.md
```

That Markdown is a projection. Regenerate it whenever it disagrees with committed recovery state; never mutate recovery authority to match prose. Keep the projection outside canonical source; writing `HANDOFF.md` into the checkout is repair/recovery self-contamination, not a convenience.

Resume into a new empty workspace/container:

```bash
make recovery-resume \
  RECOVERY_STORE=/durable/oh-goon-recovery \
  RECOVERY_DESTINATION=/new/empty/workspace
```

`recovery-status`, `recovery-checkpoint`, and `recovery-resume` verify the committed continuation object as part of the recovery graph. Digest mismatch, authority mismatch, missing continuation state, or stale CAS lineage fails closed. Filesystem recovery commands also fail before publication/restoration when the store, continuation input, or requested restore destination is inside the current canonical source root. This prevents the recovery mechanism from changing the source identity merely by staging its own artifacts.

## Session-start recovery procedure

A fresh session starts with no assumptions about previous conversation or container state:

1. Locate the persistent recovery store named by the campaign/operator handoff mechanism.
2. Run `recovery-status` and verify committed HEAD, publication receipt, archive, proof, and continuation objects.
3. Read `current_authority`, `completed_phases`, `open_phases`, `proof_receipts`, `qualification_state`, and `next_executable_phase` from the returned machine-readable continuation state.
4. Resume/materialize the exact committed source into a new disposable workspace.
5. Verify the resumed canonical source identity equals committed HEAD.
6. Execute only `next_executable_phase`; do not reconstruct additional work from memory.
7. Run the phase proof and preserve PASS/FAIL/INCOMPLETE exactly.
8. Update the continuation input ledger, create the next durable checkpoint, and independently read it back **before** starting or relying on further mutable work. Only that committed child may select the next executable phase.

If durable state cannot be read and verified, continuation is blocked. Chat history, model memory, local shell history, or a surviving partial workspace must not be used as a substitute recovery channel.
